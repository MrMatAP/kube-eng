# Defer RustFS OIDC integration, use native IAM accounts instead

We built out OIDC federation between the local IdP and the local S3 (RustFS): `idp_client` gained a `callback_url` input and a returned `client_secret` (with the `module.no_log_values` pitfall it's easy to trip over — see `library/idp_client.py`), and `infra_apply.yml`'s "Create an IdP client for S3" task registered that client and fed its id/secret into the `RUSTFS_IDENTITY_OPENID_*` container env block. RustFS's OIDC login flow doesn't quite work end to end, so that wiring is being deferred rather than pursued further right now.

Instead, S3 access is granted through RustFS's own IAM system, which mirrors MinIO's admin API (`/rustfs/admin/v3/`, undocumented but verified empirically against a live instance): `module_utils/s3_utils.py`'s `S3Admin` gained account/policy facilities (`account_create`, `account_role_set`, `account_ensure`, `account_remove`), and a new `library/s3_client.py` Ansible module wraps them. Each consuming service gets its own dedicated account (an access key/secret key pair keyed by that service's identity, not shared credentials) with exactly one of three roles selected at invocation, mapped to RustFS's canned policies: `admin` → `consoleAdmin`, `contributor` → `readwrite`, `viewer` → `readonly`.

`idp_client`/`idp_utils` themselves are generic (any client, not S3-specific) and are unaffected — they stay as-is for the next service that actually needs OIDC. Only the S3-specific OIDC wiring in `infra_apply.yml` (the "Create an IdP client for S3" task and the `RUSTFS_IDENTITY_OPENID_*` env block) is disabled, commented out with a pointer to this ADR, so it's cheap to pick back up once RustFS's OIDC support is usable. `infra_s3_config.client_roles` (the Keycloak-role side of the deferred OIDC design) is left in place for the same reason.
